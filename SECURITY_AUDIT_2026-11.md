# Security Audit — JunctionRelay_Shaders — 2026-11

Date: 2026-11-16
Scope: this repository only — `serve.py`, `test.html`, `poc/*.html`, `scripts/test_linux.sh`, `scripts/test_windows.ps1`, `packages/sdk` (`src/index.js`, `src/glslToHlsl.js`, `src/__tests__/shaders.test.js`), the 12 shader package manifests and 19 `.glsl` files under `shaders/`, the root and SDK manifests, `package-lock.json`, `README.md`, and the full git history (single commit, 67 objects, 46 blobs). The 2026-11-15 audit set (`0_Documentation/10_Security` in `JunctionRelay_Build_Scripts`) has no Shaders page; this fills that gap.
Method: read-only review of tracked source, manifests and lockfile, plus execution of the code under review — the repository's own test command on `main` and on this branch; direct invocation of `validateManifest` and `convertGlslToHlsl` from the checked-out SDK on crafted manifests; WHATWG URL-resolution measurements of `test.html`'s `?path=` handling; `scripts/test_windows.ps1` statements replayed verbatim under PowerShell 7.6.9 against crafted shader folders in an isolated directory outside the repository; a running `serve.py` probed over loopback and over the container's routed address; `npm ci`, `npm audit` (online, `--package-lock-only`, `--omit=dev`, `--offline`), `npm audit signatures`, an OSV query for the single dependency, an install-script scan of every installed package, a secret-shape sweep of the working tree and of every historical git blob, and timed runs of the converter on adversarial input.
Severity yardstick: the same one used by the 2026-11-15 audit set — High for remotely reachable auth/code-execution-class flaws with low prerequisites, Medium for weaknesses that need a LAN/adjacent position, a file/config write or user interaction, Low for robustness, hardening and supply-chain hygiene.

**This audit fixes nothing.** None of the findings below is repaired by this branch: no production file, test file, fixture, manifest, lockfile or build output was changed to address a finding. The only non-document change on the branch is one comment line in `shaders/junctionrelay.clouds/clouds.glsl`, made because the repository's own test command fails on `main` without it; it is not a security fix and closes none of the findings. See **Test status**.

This report contains no secret values. It records locations, kinds of issue, severity, attacker prerequisites, confirmation status and one-line fixes. There were in any case no secrets to reproduce.

## Findings

### S-01 — Medium — `serve.py` binds every interface and serves the entire developer working tree, including `.git`

- Location: `serve.py:59` (`http.server.HTTPServer(("", PORT), http.server.SimpleHTTPRequestHandler)` — an empty host string binds all interfaces), `serve.py:6` (`os.chdir(os.path.dirname(os.path.abspath(__file__)))` makes the document root the repository working tree, not a build or shaders directory), `serve.py:5` (fixed port 8080), `serve.py:28` and `serve.py:63` (the URL it prints and hands to the browser is `http://localhost:8080/…`, which tells the operator the service is loopback-only when it is not).
- Kind: information disclosure / missing access control / cleartext HTTP (CWE-200, CWE-306, CWE-923). No authentication, no host or origin check, directory listing on.
- Measured in this run: the listener is `00000000:1F90` in `/proc/net/tcp` (`0.0.0.0:8080`), and requests to the container's routed address `172.17.0.2:8080` succeeded — `GET /` 200 (directory listing), `GET /.git/config` 200, `GET /.git/HEAD` 200, `GET /shaders/` 200 (listing), `GET /node_modules/` 200, and a gitignored scratch file placed in the tree was served 200. Requests are logged to the operator's console. Traversal above the document root is **not** possible: `GET /shaders/../../../etc/hostname` returns 404 (`SimpleHTTPRequestHandler` normalises the path).
- What an attacker would need: network reachability to TCP 8080 on the machine running `serve.py` (same LAN, VPN or container bridge) while it runs. No credentials, no interaction with the developer, and the developer never learns the port is reachable — the console only prints localhost-style usage. Practical payload: `.git/` (config, refs and objects — the whole repository can be reconstructed, and a remote URL in `.git/config` is a common place to find a credential-bearing HTTPS remote) plus any gitignored file a developer keeps in the checkout (`.env`, key material, IDE and database files).
- Confirmation: **confirmed and measured.**
- Suggested fix: bind loopback (`HTTPServer(("127.0.0.1", PORT), …)`) and serve from a staging directory that holds only `test.html` and `shaders/`, never a git working tree.

### S-02 — Medium — `scripts/test_windows.ps1` interpolates untrusted directory and manifest names into a `node -e` program, giving code execution

- Location: `scripts/test_windows.ps1:25` (`$name`, the shader directory name from `Get-ChildItem "shaders" -Directory` at `:18`, interpolated into a single-quoted JavaScript string inside a double-quoted PowerShell argument: `node -e "…require('./shaders/$name/package.json')…"`), and `scripts/test_windows.ps1:39` (`$pkgPath`, `$hlslFile` and `$glslPath` interpolated into three single-quoted JavaScript strings in one `node -e` argument; `$glslPath` is `Join-Path $shaderDir.FullName $entry` at `:32`, where `$entry` is `junctionrelay.passes[].entry` from the shader manifest, read at `:25`).
- Kind: injection into a command line (CWE-94/CWE-88). Nothing validates a directory name or an `entry` value, and `'` is a legal character in Windows (and Linux) file names, so a name or entry containing `'` terminates the JavaScript string literal and leaves the rest at statement position.
- What an attacker would need: to place one crafted directory (or third-party shader package folder — `README.md:30-40` tells authors to copy a shader folder into `shaders/`, and `README.md:109` allows third-party namespaces) under `shaders/`, then have a maintainer or CI job run `.\scripts\test_windows.ps1`, which `README.md:232` and `README.md:244-247` describe as the required Windows test. It runs as that maintainer, so it is a developer/CI-side compromise, not something a shader consumer or a display reaches over the network.
- Confirmation: **confirmed and executed** here, against verbatim copies of the two statements in an isolated directory outside this repository (PowerShell 7.6.9, node 22): with a directory named `x'+require('node:fs').writeFileSync('PWNED-line25','pwned')+'`, the statement from `:25` wrote the marker file — arbitrary Node execution as the maintainer; with a manifest `entry` of the same shape, the statement from `:39` threw a custom `Error` from inside the generated JavaScript, proving execution on that line as well. Windows-specific path shapes were not exercised (no Windows host in this environment).
- Suggested fix: do not build JavaScript on the command line — put the conversion in a committed `.js` file and pass the paths as `process.argv` (or an environment variable), and reject any shader directory whose name is not `junctionrelay.<name>`-shaped before touching it.

### S-03 — Medium — a manifest's `passes[].entry` path is never contained, so a shader package can make tools read outside its own folder

- Location: `packages/sdk/src/index.js:43-46` — `validateManifest`, the SDK's published manifest gate, accepts any `pass.entry` for which `typeof pass.entry === 'string'`; consumed uncontained at `packages/sdk/src/__tests__/shaders.test.js:174-175` (`path.join(shaderDir, pass.entry)` then `fs.existsSync`, then `readFileSync` at `:281`, `:299`, `:304`, `:485`), at `test.html:196` (`fetch(`${shaderPath}/${pass.entry}`)`), and at `scripts/test_windows.ps1:32` (`Join-Path $shaderDir.FullName $entry`, which is what feeds S-02). No `path.basename`, no `resolve` + prefix check, no pattern.
- Kind: path traversal (CWE-22) — a plugin-supplied path fragment joined onto a root with no containment, in the same class the 2026-11-15 audit recorded host-side as X6.
- What an attacker would need: to author a shader package whose manifest declares, for example, `"entry": "../../../../../../etc/passwd"` and have a developer drop it into `shaders/` (or a host install it). That is a file write / install action, not a network position. Once installed, every tool that walks `shaders/` follows the manifest out of the package directory.
- Confirmation: the gap is **confirmed in this repository and measured** — `validateManifest({junctionrelay:{type:'shader',shaderName:'acme.evil',passes:[{entry:'../../../../../../etc/passwd'}],uniforms:[]}})` returns `{"valid":true}`, so the SDK offers no gate for its own consumers. What the XSD host does with `entry` at install and run time is outside this repository and is **unconfirmed** here (recorded as X6 in the 2026-11-15 XSD page).
- Suggested fix: reject any `entry` that is not a bare file name (e.g. `/^[A-Za-z0-9._-]+\.glsl$/`) in `validateManifest`, and have every consumer resolve the joined path and verify it is still inside the shader directory.

### S-04 — Low — `test.html` builds same-origin fetch URLs from the raw `?path=` query parameter

- Location: `test.html:157-159` (`params.get('path')` becomes `shaderPath = \`shaders/${shaderName}\`` with no validation), consumed at `test.html:171` (`fetch(`${shaderPath}/package.json`)`) and, second-order, at `test.html:196` (`fetch(`${shaderPath}/${pass.entry}`)`, where `entry` comes from the fetched manifest — S-03).
- Kind: client-side path traversal / unvalidated URL fragment (CWE-22).
- What an attacker would need: user interaction — to get the developer to open a crafted link against their own running `serve.py`, e.g. `test.html?path=a/../../.git/config`. Measured with the WHATWG URL parser against `http://127.0.0.1:8080/test.html`: `a/../../.git/config` resolves to `http://127.0.0.1:8080/.git/config`, `../../package-lock.json` to `/package-lock.json`, and `..\..\windows\win.ini` to `/windows/win.ini` (backslashes are separators in `file:`/`http:` URLs, so the Windows form works too). It is **not** an SSRF or redirect primitive: because the value is always appended after `shaders/`, the measured values `//evil.com/x`, `http://evil.com/x` and `\\evil.com\x` all resolve inside the same origin and can never form a cross-origin URL.
- Impact today: the page can be made to read arbitrary files that the server exposes (per S-01, the whole working tree). The fetched text is only handed to `gl.shaderSource`; compile failures write `getShaderInfoLog` fragments to the console (`test.html:561`, `:576`). Nothing in this page sends data anywhere, so there is no exfiltration channel out of the developer's browser from here.
- Confirmation: the URL-resolution behaviour is **confirmed by measurement**; end-to-end exploitation in a browser was not attempted.
- Suggested fix: accept `path` only when it matches the shader-directory form (`/^[a-z][a-z0-9]*(-[a-z0-9]+)*$/`) and otherwise fall back to the repository root listing.

### S-05 — Low — manifest uniform names are emitted verbatim into generated shader source, and the SDK validator does not enforce the documented identifier pattern

- Location: `packages/sdk/src/glslToHlsl.js:57-60` (`` `  ${uniformHlslType(u.type)} ${u.name};` `` joined into the `cbuffer CustomUniforms : register(b1)` header), the same pattern on the web path at `test.html:494-497` (`` `uniform vec3 ${u.name};` ``); the gate is `packages/sdk/src/index.js:51`, which only checks `typeof u.name === 'string'`; the contract `README.md:180` says the name `must match [a-zA-Z_]\w*`, and that pattern is enforced only inside this repository's own test (`packages/sdk/src/__tests__/shaders.test.js:212`).
- Kind: injection into generated source at a compiler boundary (CWE-74/CWE-94).
- What an attacker would need: the same as S-03 — to ship a shader package manifest, since uniform names are manifest data. The impact stays inside the shader stage (an arbitrary pixel shader already runs arbitrary GPU code by design, which is this product's model), so this is not host code execution; what it breaks is the assumption that only declared scalars reach the constant buffer the host binds, because the generated HLSL/GLSL itself is attacker-shaped.
- Confirmation: **confirmed by execution** of the checked-out SDK: `validateManifest` returns `{"valid":true}` for the name `x}; float4 evil; cbuffer Z : register(b2) { float a;`, and `convertGlslToHlsl` emits it into the header verbatim as `float x}; float4 evil; cbuffer Z : register(b2) { float a;;`, i.e. arbitrary HLSL on its way to `fxc` (and, via `test.html`, arbitrary GLSL to WebGL).
- Suggested fix: validate `u.name` against `/^[a-zA-Z_]\w*$/` in `validateManifest` and skip (never emit) a non-conforming name in `convertGlslToHlsl`.

### S-06 — Low — the GLSL compile harness uses predictable file names in the shared temp directory and then executes one of them

- Location: `packages/sdk/src/__tests__/shaders.test.js:73-74` (`tmpFile = os.tmpdir()/spirv_test_<pid>.glsl`, `scriptFile = os.tmpdir()/spirv_test_<pid>.js`), written at `:76` and `:78` with plain `fs.writeFileSync` (which follows a pre-existing symlink), executed at `:91` (`execSync(\`node ${JSON.stringify(scriptFile)}\`)`), unlinked at `:100-101`.
- Kind: insecure temporary file / symlink TOCTOU (CWE-377, CWE-59).
- What an attacker would need: a second local identity — any user or process that can create entries in the shared `/tmp` on a multi-user box (kiosk/Pi hosts and shared CI runners are the realistic case; a single-user workstation is far less exposed) — racing the pid-derived name. On the `.js` path the file is executed by `node`, so content substituted between the write and the exec runs as the developer or CI user; on the `.glsl` path a pre-created symlink is written straight through to its target.
- Confirmation: the unsafe pattern is **confirmed in code**; no exploit was attempted.
- Suggested fix: create a private directory once per run with `fs.mkdtempSync(path.join(os.tmpdir(), 'jr-spirv-'))` (mode 0700) and open both files with `flag: 'wx'`.

### S-07 — Low — `convertGlslToHlsl` is quadratic in the number of matrix declarations, so a small shader file can pin a CPU

- Location: `packages/sdk/src/glslToHlsl.js:178-192` (`replaceMatrixMultiply`: it collects every matrix declaration at `:180-184`, then for each one runs a full-document regular-expression replace twice, `:186-189`). Every `.glsl` file in `shaders/` is pushed through it by `packages/sdk/src/__tests__/shaders.test.js:367` (and through `convertPass` at `:545`) and by `scripts/test_windows.ps1:39`, so it is on the validate-at-load path this repository owns.
- Kind: algorithmic complexity → CPU exhaustion (CWE-407).
- Measured on the checked-out code (node 22, this container): 200 matrix declarations (4.6 KB source) → 14.8 ms; 1 000 (23 KB) → 244 ms; 4 000 (95 KB) → 3 993 ms. That is super-linear (≈ O(n²)), so a single ~1 MB shader costs minutes of CPU per pass, and one test or CI run converts every pass of every directory found under `shaders/`.
- What an attacker would need: as in S-03/S-05 — to get one shader package with a padded `.glsl` file into `shaders/` (or into a host that converts on load, which is outside this repository) and let the maintainer run the ordinary test command. Memory and output size stayed proportional; the blank-line collapse loop at `glslToHlsl.js:132-134` was measured linear in practice (800 KB → 17 ms) and no catastrophic-backtracking regex was found in the converter.
- Confirmation: **confirmed by measurement.**
- Suggested fix: gather the matrix names once and rewrite in a single pass over the text (one alternation regex or a small tokenizer) instead of one full-document replace per declaration.
